## Emulation rule(mandatory)

🔷 **webview2-gtk exists to emulate WebKitGTK** so shared Vala can `#if WINDOWS` / `#else` with the same shapes.

- 🔷 Copy **exact names / signals / properties** from **webkitgtk-6.0**.
- 🚫 Do **not** invent public click/type APIs on `WebView`.
- 🚫 Do **not** invent a “local WebDriver HTTP endpoint” inside this library. On Linux the HTTP server is the **external** `WebKitWebDriver` process — not WebKitGTK and not the app.

---

## Two layers(do not conflate)

### A. Input / fill commands(app → driver) — **not a WebView API**

Fill delivery is **libsoup(or equivalent) HTTP** to **WebKitWebDriver**:

```
app fill client  --HTTP POST-->  WebKitWebDriver(-p <wd>)  --inspector -t-->  browser WebView
```

Examples that returned `unsupported operation` in smoke:

- `POST /session/.../element/.../click`
- `POST /session/.../element/.../value` (Send Keys)
- Actions pointer click

🔷 **There is no WebKitGTK Vala API for these.**  
🔷 **webview2-gtk does not implement these as `WebView` methods.**  
🔷 The app never “calls into WebView” for click/sendKeys; it POSTs to the driver.

Ubuntu GTK4 failure is inside `libwebkitgtk` (interactions compiled out) after the driver forwards the command — fixed by Snappr 2.11.1 packaging, not by adding Vala APIs here.

### B. Browser automation setup(app → WebKitGTK) — **this plan’s WebView/WebContext surface**

What `tests/automation-browser/main.vala` actually calls — **emulate these**:

```vala
WebContext.get_default().set_automation_allowed(true);
/* WebView construct: */ is_controlled_by_automation = true;
context.get_network_session_for_automation();
context.automation_started.connect((session) => {
	session.set_application_info(info);
	session.create_web_view.connect(() => view);
});
Environment.set_variable("WEBKIT_INSPECTOR_SERVER", "127.0.0.1:<port>", true);
```

## Purpose

- 🔷 Emulate the **WebKitGTK automation skeleton** (`WebContext` / `WebView` / `AutomationSession` / `ApplicationInfo`) so the same browser-side setup works on Windows.
- 🔷 Support attach of an external driver via the same inspector-listen idea(`WEBKIT_INSPECTOR_SERVER` / equivalent) so fill can stay **HTTP → driver**, not new WebView APIs.
- ℹ️ If the Windows driver path needs the host to actually move the mouse/type in-page, that is **host-internal** (e.g. CDP) behind the automation/inspector attach — **not** a public `WebView` input API and **not** a WebDriver HTTP server inside webview2-gtk.
