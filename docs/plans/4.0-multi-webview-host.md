## Emulation rule (mandatory)

🔷 Public API stays WebKitGTK-shaped (`WebView`, `load_uri`, `load_changed`, …). Multi-instance is an **internal** host fix so two GTK `WebView`s behave like two WebKit views (separate documents), not a new Windows-only public surface.

🚫 Do not invent “claim active view” / “set_active_webview” public APIs.

---

## Purpose

- 🔷 Match the original design assumption: **each GTK `WebView` owns a real WebView2 browser** (controller + document).
- 🔷 Inactive views stay parked off-screen (`PutBounds` at −30000) on **their own** controller — not disconnected from a shared singleton.
- 🔷 Fix paned-insert: management + primary both attach; primary `load_uri` gets `load_changed` on **that** widget.
- 🔷 Remove the documented “one host per process” lie once this lands (README + `webview.vala` limitation comment).

---

## What was assumed vs what shipped

| Assumed design | What v0.1 actually did |
|----------------|-------------------------|
| N GTK `WebView` → N `ICoreWebView2Controller` | One `g_host` / `g_glue` for the process |
| Inactive controller parked off-screen | One controller; second `create_with_xywh` **overwrites** globals |
| Each view keeps its own URI / history / events | `get_uri` / events / bounds all hit the singleton |
| Destroy one view = destroy its controller | Any destructor can tear down the only host |

WebView2 itself supports the assumed model: **one Environment (optional share) → many `CreateCoreWebView2Controller(parent_hwnd)` → each `PutBounds`**. The choke is this library’s host API with no instance handle.

---

## Wrong “fixes” (🚫)

- 🚫 **Park-and-claim one controller** (move bounds + rebind event `user_data` to the visible widget). Still one document/history; URI/title bleed across widgets; not the design.
- 🚫 **Second `create_with_xywh` overwrites `g_host`** (today). Leaks the old controller, steals callbacks, leaves other widgets `attached == true` with no host.
- 🚫 Public “active WebView” switcher — WebKit doesn’t have that; apps just show/hide widgets.

---

## Target architecture

```text
                    ┌─────────────────────────────┐
                    │ ICoreWebView2Environment    │  💩 prefer one shared env
                    │ (CDP port / autoplay opts)  │     created on first attach
                    └─────────────┬───────────────┘
                                  │ CreateCoreWebView2Controller × N
              ┌───────────────────┼───────────────────┐
              ▼                   ▼                   ▼
        HostInstance A      HostInstance B      HostInstance …
        controller+webview  controller+webview  …
        bounds / pending    bounds / pending
        event tokens        event tokens
        user_data → WebView* user_data → WebView*
              ▲                   ▲
              │                   │
        WebView (GTK) A     WebView (GTK) B
        park if !shown      park if !shown
```

**Per `HostInstance`:** parent HWND, bounds, controller, webview, ready, pending_url, visible flag, COM event tokens, pointer back to owning `WebView`.

**Per GTK `WebView`:** owns one `HostInstance` for life of `attached`; destructor only releases **its** instance.

**Inactive:** that instance’s `PutBounds(-30000,-30000,…)` / keep `IsVisible` as today for DevTools — same park logic, applied to **that** controller.

## Work slices

### 4.1 Host API becomes instance-keyed ✅

**Why:** Every `vala_webview2_host_*` today has no handle — impossible to address two controllers.

**Where:** `lib/host/webview2gtk-host-api.h`, `win32-ui-webview2-host.vala`, `win32-ui-webview2-com-glue.c`, generated host-glue.

**Do:**

- 🔷 Introduce opaque `WebView2Host*` (or `uint64 id`) returned from create; all navigate / bounds / getters / destroy take it.
- 🔷 Replace `g_host` / `g_glue` with a table or embed state in the handle.
- 🔷 `com_begin_host` must **not** `ZeroMemory` a process singleton; allocate per instance; async completion writes **that** instance only.
- 💩 Keep a thin Vala wrapper on `WebView` that stores `private void* host_handle` so call sites stay readable.

**Done when:** two creates → two live controllers; destroy(A) leaves B working.

### 4.2 Shared Environment (one) + N controllers ✅

**Why:** Env options (inspector port, autoplay) are process-scoped at create time; sharing one env is cheaper and matches existing automation docs.

**Where:** `win32-ui-webview2-loader.c`, `win32-ui-webview2-com-glue.c`, `win32-ui-webview2-automation.c`.

**Do:**

- 🔷 First attach creates Environment; later attaches reuse it (`CreateCoreWebView2Controller` only).
- 🔷 Refcount env; release when last controller is destroyed.
- ℹ️ Separate user-data folders per view only if we later need cookie isolation (⏳); default shared profile is OK for v1 multi-instance.
- 💩 Document: still one CDP port / env — automation remains process-scoped.

**Done when:** two widgets, one env, two controllers; `WEBKIT_INSPECTOR_SERVER` still works.

### 4.3 Per-instance event and feature modules ✅

**Why:** Nav / script / download / resource / permission / doc-response handlers are process-global `g_*` slots — last attach wins (paned-insert failure mode).

**Where:** `webview2gtk-host-listeners.vala`, `lib/host/win32-ui-webview2-events.c`, `win32-ui-webview2-{document-response,script-messages,downloads,web-resources,permissions}.c`.

**Do:**

- 🔷 Register COM handlers with `user_data = HostInstance*` (or owning `WebView*`).
- 🔷 Emit into **that** widget’s signals only.
- 🔷 Script message names / download jobs keyed by instance (or demux by `sender` webview).
- 🔷 `set_event_handlers` becomes per-handle (or set at create and never global).

**Done when:** management `load_changed` and primary `load_changed` both fire for their own navigations; no cross-talk.

**Landed (2026-08-24):** nav/title, document-response, script-messages, downloads, web-resources, permissions per-host. Sync helpers (`execute_script_sync`, cookies, capture, print, a11y walk) take `WebView2Host*`. Download jobs remain a process-global id table (each job holds `host`). Shared cookie profile / CDP env remain process-scoped by design.

### 4.4 Widget attach / park / destroy ✅

**Why:** `webview.vala` `try_attach` assumes create always owns “the” host.

**Where:** `lib/webview2gtk/webview.vala`, Win32Atspi register.

**Do:**

- 🔷 `try_attach`: create **this** instance; store handle; wire handlers to `this`.
- 🔷 `sync_host_visible` / `push_bounds`: only touch **this** handle’s bounds.
- 🔷 `~WebView`: destroy **this** handle only; clear `attached`.
- 🔷 Win32Atspi: map WebView → instance (or focused/visible); stop “last register wins” as the only tree. — ✅ `register_webview` keeps every live view; `get_desktop` exposes one `document frame` per host (match by name / URI).
- 🔷 Delete limitation comments once green.

**Done when:** paned-insert `--smoke` → `TEST_PASS`; single-view hello/browser still pass.

### 4.5 HWND / Z-order / present (risk)

**Why:** All controllers are parented to the **same toplevel** HWND today (`gdk_win32_surface_get_handle`). N Chrome children under one parent can confuse `present_webview` / EnumChildWindows / a11y walk.

**Do:**

- 💩 Spike early: two controllers, same parent, different bounds — confirm both paint and park correctly.
- ⏳ If Z-order fights: give each `DrawingArea` a real child HWND (heavier GDK/Win32 work) — only if spike fails.
- ✅ A11y: walk each host; pick that controller’s `Chrome_WidgetWin_1` by bounds when several share the toplevel.

**Done when:** spike notes in this plan; either “same parent OK” or follow-up task for child HWNDs.
