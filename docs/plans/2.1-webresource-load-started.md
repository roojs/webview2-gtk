## Emulation rule (mandatory)

🔷 This library **only emulates existing WebKitGTK APIs** so shared Vala (`#if WINDOWS` / `#else`) can use the same shapes.

- 🔷 Copy names, signals, and argument types from **WebKitGTK 6** (`webkitgtk-6.0`).
- 🔷 Approximate imperfect WebView2 COM behaviour **inside the host** so callers still see the WebKit contract.
- 🚫 Do **not** invent Windows-only public APIs, signals, or helpers that Linux WebKit does not have.
- 🚫 Do **not** expose settle / quiet / network-idle helpers — those belong in the app, built on this surface.
- 🚫 Do **not** put consumer-app product names, plans, or workflows in this document.

---

## Purpose

- 🔷 Emulate WebKitGTK `WebView.resource_load_started` + `WebResource` lifecycle so callers can count in-flight subresources.
- 🔷 Reuse / extend the existing host path that already listens for `WebResourceResponseReceived` (main-document filter today for `main_document_response`).

---

## API copied from WebKitGTK 6

Canonical (from `webkitgtk-6.0` vapi — implement the **subset** needed for load tracking; do not invent extras):

```vala
public sealed class WebResource : GLib.Object {
	public unowned string get_uri ();
	public string uri { get; }
	public signal void finished ();
	public signal void failed (GLib.Error error);
	// Optional later if a caller needs them — only if WebKit has them:
	// get_data, get_response / response, sent_request, failed_with_tls_errors
}

// on WebView:
public signal void resource_load_started (
	WebResource resource,
	URIRequest request
);
```

`URIRequest` already exists (`uri` only) — enough for this signal’s second argument.

---

## Host mapping (internal — not public API)

Map WebView2 COM onto the WebKit shapes above:

- 🔷 `WebResourceRequested` (+ `AddWebResourceRequestedFilter("*", ALL)`) → construct `WebResource` + `URIRequest` → emit `resource_load_started`
- 🔷 `WebResourceResponseReceived` (URI FIFO match) → emit `WebResource.finished`
- 🔷 Destroy / unregister → `WebResource.failed` for still-pending resources
- 💩 ResponseReceived is closer to “response started” than WebKit body-complete `finished` — approximate inside the host; public API stays WebKit-named
- ℹ️ Keep existing **main-frame document** filter for `main_document_response` unchanged — resource signals are a separate COM subscription

---

## Out of scope

- 🚫 App-level “wait until network quiet” loops or timeouts
- 🚫 Header rewrite / Cookie injection on `resource_load_started` (WebKit allows header access; this port historically unreliable — do not expand unless matching a documented WebKit consumer need)
- 🚫 Full `WebResource` parity (`get_data`, TLS failure signals) unless a later plan copies those WebKit members explicitly
- 🚫 `decide_policy` / `ResponsePolicyDecision` (separate WebKit surface; not this plan)
